# hickory-dns advisories: affected ranges checked against released source (2026-11-13)

Licence: CC BY 4.0. Prepared with AI agents working for MV2 of Munim, Inc. (mv2@munimtech.com).

Before drafting RustSec entries for the hickory-dns advisories published on 2026-09-03, we read the code each fix changes in the releases on both sides of every upstream range boundary (tagged source on GitHub, and docs.rs for the 0.26.1/0.26.2 pair). For six of the eleven advisories checked in the 2026-11-13 batches (57pw, 3jvh, wjgj, j2rc, vrv5, xv7c, 3w89, 29q9, vcjp, 9px7, 2hxp), the affected ranges listed upstream don't match the code. In each case the fix itself is correct and is in the 0.26.2 releases. Only the version ranges differ.

| Advisory | Upstream range | What the source shows | Effect |
|---|---|---|---|
| GHSA-3w89-7rx5-hpwx (CVE-2026-123578), UDP response with QDCOUNT=0 skips the question check | hickory-proto 0.25.0 .. 0.25.2; hickory-net 0.26.0 .. 0.26.1 | The same one-way check, `response_queries.iter().all(\|elem\| request_queries.contains(elem))`, which is true for an empty question section, is in hickory-proto v0.25.0-alpha.1 and v0.26.0-alpha.1 and in hickory-net v0.26.0-beta.1. hickory-proto 0.24.4 has no question check at all (a TODO). | Upstream misses the 0.25.0 alphas, 0.26.0-alpha.1 and the four hickory-net 0.26.0 betas. |
| GHSA-3jvh-8vj5-65rq (CVE-2026-123600), NSEC3 apex NODATA without an H(QNAME) match | hickory-proto 0.25.0-alpha.3 .. 0.25.2; hickory-net "0.26.0-alpha.1 .. 0.26.1" | hickory-net's first release is 0.26.0-beta.1. 0.26.0-alpha.1 is a hickory-proto release, and its `nsec3_validation.rs` still has the vulnerable `(None, None, None) if query_name == soa_name => Proof::Secure` arm. | Upstream misses hickory-proto 0.26.0-alpha.1. |
| GHSA-xv7c-h5g9-x25x (CVE-2026-123597), transient DS-fetch error cached as bogus | hickory-proto v0.25.0-alpha.1 .. 0.26.0-alpha.1; hickory-net 0.26.0-beta.1 .. 0.26.1 | In hickory-proto v0.25.2 and v0.26.0-alpha.1, `fetch_ds_records` also turns a lookup error into `ds_should_exist`, but `DnssecDnsHandle` has no validation cache in any hickory-proto release checked (v0.25.0-alpha.1, v0.25.2, v0.26.0-alpha.1; its fields are the inner handle, trust anchors, request depth and limits). `ValidationCache` and its `ProofErrorKind::Net` guard first appear in hickory-net 0.26.0-beta.1. | The "cached for the whole zone" effect the advisory describes can't happen in hickory-proto, so the hickory-proto range looks over-broad. |
| GHSA-29q9-p769-j8gq (CVE-2026-123598), DNSSEC-bogus answers cached for the attacker-supplied TTL | hickory-resolver 0.26.0-alpha.1 .. 0.26.1; hickory-recursor 0.25.0 .. 0.26.0-alpha.1; hickory-net 0.26.0-beta.1 .. 0.26.1 | From hickory-proto v0.25.0-alpha.1, `DnssecDnsHandle` keeps RRsets that fail validation in the response and marks them with their proof ("all records are returned, it's up to downstream users to check for correctness"). hickory-resolver's `CachingClient` sends every positive answer to `DnsLru::insert` with the smallest record TTL, capped at one day by default (v0.25.0-alpha.1, v0.25.2, v0.26.0-alpha.1). In v0.24.4, RRsets that fail validation are filtered out instead. The hickory-recursor crate first validates in v0.25.0-alpha.2 (`DnssecPolicy::ValidateWithStaticKey`, answers written back to its `DnsLru` record cache), and crates.io has no hickory-recursor 0.25.0: 0.25.0-alpha.5 is followed by 0.25.1. The hickory-net range matches the source. | Upstream misses hickory-resolver 0.25.0-alpha.1 .. 0.25.2 (stub resolver with validation) and hickory-recursor 0.25.0-alpha.2 .. 0.25.0-alpha.5. |
| GHSA-vcjp-57rr-mpfw (CVE-2026-123583), no bailiwick filtering on negative responses | hickory-recursor 0.25.0 .. 0.25.2 (no fix); hickory-resolver 0.26.0 .. 0.26.1 | The recursor moved into hickory-resolver in v0.26.0-beta.1 (`crates/resolver/src/recursor/handle.rs`). At that tag, the error branch stores the negative response unfiltered (`response_cache.insert(query, Err(error.clone()), now)`) and `answer_filter` runs only on successful responses. In hickory-recursor, `is_subzone` filtering of successful lookups first appears in v0.25.0-alpha.1; the error branch is unfiltered there and in v0.25.2, and v0.24.4 has no bailiwick filtering on any response. crates.io has no hickory-recursor 0.25.0. | Upstream misses hickory-resolver 0.26.0-beta.1 .. beta.4 and hickory-recursor 0.25.0-alpha.1 .. alpha.5 (and, more broadly, 0.24.x, which filters nothing). |
| GHSA-9px7-7m25-f6q2 (CVE-2026-123588), empty name server pool cached after failed glue lookups | hickory-recursor `*` (no fix); hickory-resolver 0.26.0 .. 0.26.1 | At hickory-resolver v0.26.0-beta.1, `ns_pool_for_name` checks `config_group.is_empty()` only to decide whether to look up NS addresses, then builds and caches the pool with no second check (same at v0.26.1; v0.26.2 returns "no glue found for any nameservers for zone"). hickory-recursor v0.24.4 and v0.25.2 behave the same. | Upstream misses hickory-resolver 0.26.0-beta.1 .. beta.4. The hickory-recursor range matches. |

GHSA-2hxp-x833-73f7 (CVE-2026-123602, ghost domain via refreshed child-side NS answers) lists hickory-resolver from v0.26.0-beta.1, which matches where the recursor code lives. We confirmed that the mitigation (`upsert_clamped_ttl` for NS queries) is in v0.26.2 and not in v0.26.1. We did not trace the older hickory-recursor releases for that one.

## What we did with this
- 3jvh: the RustSec draft covers hickory-proto 0.26.0-alpha.1 (`unaffected = ["< 0.25.0-alpha.3", ">= 0.26.0-beta.1"]`) and says so in the pull request, offering to narrow it.
- 3w89: the RustSec draft uses `patched = [">= 0.26.2"]` for hickory-net (every release before the fix) and `unaffected = ["< 0.25.0-alpha.1", ">= 0.26.0-beta.1"]` for hickory-proto.
- xv7c: the RustSec draft has a hickory-net entry only, and explains why there is no hickory-proto entry, offering to add one that matches the upstream range.
- 29q9: the RustSec draft uses `unaffected = ["< 0.25.0-alpha.1"]` for hickory-resolver and `unaffected = ["< 0.25.0-alpha.2"]` (no fixed release) for hickory-recursor, and says so in the pull request, offering the upstream ranges instead.
- vcjp, 9px7, 2hxp: the RustSec drafts use `unaffected = ["< 0.26.0-beta.1"]` for hickory-resolver and `patched = []` for every hickory-recursor release, offering `unaffected = ["< 0.25.0-alpha.1"]` for vcjp if the reviewers prefer upstream's intent.
The RustSec reviewers decide; these notes only record what the code shows.

## How to check
- Tagged source: `https://raw.githubusercontent.com/hickory-dns/hickory-dns/<tag>/crates/proto/src/udp/udp_client_stream.rs` (v0.24.4, v0.25.0-alpha.1, v0.26.0-alpha.1), `crates/net/src/udp/udp_client_stream.rs` (v0.26.0-beta.1), `crates/proto/src/dnssec/dnssec_dns_handle/mod.rs` (v0.25.2, v0.26.0-alpha.1), `crates/proto/src/xfer/dnssec_dns_handle.rs` (v0.24.4, v0.25.0-alpha.1), `crates/net/src/dnssec/mod.rs` (v0.26.0-beta.1).
- For 29q9: `crates/resolver/src/caching_client.rs` and `crates/resolver/src/dns_lru.rs` (v0.25.0-alpha.1, v0.25.2), `crates/resolver/src/cache.rs` (v0.26.1, v0.26.2), `crates/recursor/src/recursor.rs` (v0.25.0-alpha.1, v0.25.0-alpha.2) and `crates/recursor/src/lib.rs` (v0.25.0-alpha.2, `cache_response`).
- For vcjp and 9px7: `crates/resolver/src/recursor/handle.rs` (v0.26.0-beta.1, v0.26.1, v0.26.2), `crates/recursor/src/recursor.rs` (v0.24.4, v0.25.0-alpha.1), `crates/recursor/src/recursor_dns_handle.rs` (v0.25.2).
- Fix commits (from hickory-dns/hickory-dns#3871): 1e60815 (3w89), ffdfb29 (3jvh), 55efddf (xv7c), 8ff4426 (29q9), fbcf69d (vcjp), ece0b7d (9px7), d96c33c (2hxp).
- crates.io: hickory-net versions start at 0.26.0-beta.1 (2026-03-12). hickory-resolver has 0.26.0-beta.1 to beta.4 (2026-03-12 to 04-14) before 0.26.0 (04-16). hickory-proto's only release before 0.24.0 is 0.1.0, a name placeholder with no library. hickory-recursor versions: 0.24.0-0.24.4, 0.25.0-alpha.1 to alpha.5, 0.25.1, 0.25.2, 0.26.0-alpha.1.

Limits: we sampled the boundary releases, not every release in between. We read the code but did not run an exploit against each release.
